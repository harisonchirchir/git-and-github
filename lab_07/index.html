GitHub Collaboration: Issues, Pull Requests, and Reviews

Git provides version control; GitHub adds tools for planning, discussing, reviewing, and governing changes. Follow work from an issue through a reviewed pull request.

Step 1: Track work with Issues

Use a GitHub Issue to describe a bug, feature, question, or task. A useful issue has a clear title, context, steps to reproduce (for a bug), expected behavior, and acceptance criteria. Labels categorize work; milestones group issues and pull requests toward a target.

Reference an issue in a branch or PR. In the PR description, keywords such as Closes #42 link and close the issue when the PR is merged into the default branch. GitHub Projects can organize issues and PRs in a table, board, or roadmap view; use the issue for the durable work description.

Step 2: Open a focused pull request

  1. Create a branch for one change and commit small, understandable updates.
  2. Push the branch and open a PR against the intended base branch.
  3. Explain what changed, why, how it was tested, and any risks. Link related issues.
  4. Keep the PR in draft while in progress; request review when ready.
  5. Keep discussion and follow-up commits on the same branch.

A draft PR invites early feedback without signaling that a change is ready to merge. A review request asks specific teammates to examine the change.

Step 3: Review and merge responsibly

Reviewers should examine the diff, check behavior and tests, ask specific questions, and approve only when the change meets repository standards. Authors should respond constructively and resolve conversations once addressed.

  • Merge commit: preserves branch commits and adds a merge commit.
  • Squash and merge: combines PR commits into one commit on the base branch.
  • Rebase and merge: replays PR commits onto the base branch without a merge commit.

The repository chooses which methods are allowed. Agree on a team policy. Delete a merged feature branch when it is no longer needed; the commits remain in merged history.

Step 4: Protect the default branch

Branch protection or repository rulesets can require PRs, approvals, status checks, resolved conversations, or signed commits. They can also restrict force pushes and deletion. Require checks that meaningfully protect quality and document who can bypass rules in emergencies. Settings can vary by repository visibility and plan.

Step 5: Contribute through a fork

When you do not have write access, fork the repository, clone your fork, and add the original as upstream:

git clone https://github.com/YOUR-USER/PROJECT.git
cd PROJECT
git remote add upstream https://github.com/OWNER/PROJECT.git
git switch -c fix/issue-42

Push your branch to origin (your fork) and open a PR from that branch to the original repository. Update your local default branch with the original's changes:

git fetch upstream
git switch main
git merge upstream/main
git push origin main

Check the repository contribution guide and code of conduct before contributing.

Practice: complete a PR lifecycle

  1. Create an issue with a goal and acceptance criteria.
  2. Create a feature branch named for the issue and implement the change.
  3. Open a draft PR, describe the change and testing, and link the issue.
  4. Ask a peer to review; respond to comments and update the branch.
  5. Check required status checks and merge method; merge only when requirements pass.
