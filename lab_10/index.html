Advanced Git Tools and Repository Management

Explore tools for applying individual commits, finding regressions, examining line history, using multiple worktrees, and managing dependencies or large binary assets.

Step 1: Apply one commit with cherry-pick

git cherry-pick applies an existing commit's changes to the current branch and creates a new commit. It is useful for backporting a focused fix:

git switch release-branch
git cherry-pick <commit>

The new commit ID differs because its parent differs. If conflicts occur, resolve and stage the files, then use git cherry-pick --continue; cancel with git cherry-pick --abort. Avoid broadly cherry-picking where a merge is more appropriate.

Step 2: Find a regression with bisect

git bisect binary-searches history for the commit that introduced a problem. Mark a known-bad and known-good revision:

git bisect start
git bisect bad
git bisect good <known-good-commit>

Test each checked-out revision and mark it with git bisect good or git bisect bad. When Git identifies the first bad commit, inspect it and end the session:

git bisect reset

Automate with git bisect run <test-command> when the test returns zero for good and nonzero for bad. Ensure the test works reliably across older revisions.

Step 3: Investigate file history with blame

git blame -L 20,40 path/to/file
git show <commit>

git blame shows the commit and author associated with each line. Use it to find context, not to assign fault; read the commit, PR, and related discussion.

Step 4: Work on multiple branches with worktrees

A worktree checks out another branch into a separate directory while sharing repository data:

git worktree add ../project-hotfix hotfix/urgent-fix
git worktree list
git worktree remove ../project-hotfix

A branch generally cannot be checked out in two worktrees at once. Save or commit work before removing a worktree.

Step 5: Know when submodules are appropriate

Submodules record a specific commit from another repository. They preserve independent versioning but add setup and collaboration steps:

git submodule add https://github.com/OWNER/DEPENDENCY.git vendor/dependency
git clone --recurse-submodules <repository-url>
git submodule update --init --recursive

The parent stores a pointer to a submodule commit, not its complete history. Contributors need access to the submodule repository and commit changes there before updating the pointer in the parent.

Step 6: Use Git LFS for large files

Frequently changing binaries can make Git history grow quickly. Git LFS puts small pointer files in Git and stores actual content through an LFS server; hosting providers may impose storage and bandwidth quotas.

git lfs install
git lfs track "*.psd"
git add .gitattributes
git add design.psd
git commit -m "Track design assets with Git LFS"

Commit .gitattributes so contributors know which patterns use LFS. It does not automatically shrink binaries already committed; history migration is disruptive and requires coordination.

Choosing the right tool

  • Cherry-pick: a small, specific commit on another branch.
  • Bisect: locate a regression with known good/bad revisions and a reliable test.
  • Blame: find a line's history, then investigate its context.
  • Worktrees: simultaneous checkouts in separate directories.
  • Submodules: independently versioned repositories with clear ownership.
  • Git LFS: large binary assets, after reviewing quotas and team setup.

Practice

  1. Cherry-pick a test commit onto a temporary branch and inspect it.
  2. Run git bisect on a small example with a known regression.
  3. Use blame to locate a change, then read its full commit context.
  4. Create and remove a temporary worktree.
  5. Explain how submodule pointers and LFS pointer files differ from ordinary files.
