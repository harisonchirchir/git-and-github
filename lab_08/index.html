Automating Workflows with GitHub Actions

GitHub Actions runs automation on repository events. Use continuous integration to check proposed changes and continuous delivery or deployment to publish approved changes. Workflow YAML files live in .github/workflows/.

Step 1: Understand the workflow model

  • A workflow is an automation definition.
  • An event starts it: push, pull request, schedule, or manual dispatch.
  • A job groups steps and runs on a runner.
  • A step runs a shell command or reusable action.
  • Artifacts store or pass build outputs.

Workflows can use GitHub-hosted or self-hosted runners. Treat self-hosted runners carefully because untrusted code may execute on them.

Step 2: Add a basic CI workflow

For static HTML and Python link-check code, create .github/workflows/ci.yml:

name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check internal links
        run: python3 scripts/check_links.py

On PRs, this creates a status check that branch protection can require. Application repositories should add their test, lint, and build commands. Actions are dependencies: pin to a reviewed release or immutable SHA according to policy and keep them updated. Version tags are readable examples, not immutable pins.

Step 3: Use secrets and permissions safely

Keep sensitive values in GitHub Actions secrets or environment secrets, never in workflow files or source. Expose a secret only to the step that needs it:

      - name: Publish
        env:
          API_TOKEN: ${{ secrets.API_TOKEN }}
        run: ./scripts/publish.sh

Never print secret values. Workflows from forks generally do not receive repository secrets. Avoid privileged pull_request_target workflows that check out and execute untrusted PR code.

Use the narrowest permissions required. Start with contents: read and grant write access only to jobs that need it. Prefer scoped credentials and review third-party actions before use.

Step 4: Add a deployment workflow

This repository already includes .github/workflows/static.yml, which deploys the static site to GitHub Pages on pushes to main and supports manual dispatch. Pages deployment needs pages: write and id-token: write; the CI example uses read-only permissions.

Configure Settings → Pages to use GitHub Actions. Review workflow logs and deployment environments when a run fails. For production, consider environment protection rules and approvals.

Step 5: Debug and improve workflows

  1. Open the Actions tab, select the failed run, and inspect job and step logs.
  2. Reproduce the command locally where possible.
  3. Check event filters, YAML indentation, permissions, secrets availability, and runner environment.
  4. Re-run after understanding the failure; do not expose secrets while debugging.
  5. Use caching when it measurably helps, and configure concurrency to prevent duplicate deployments.

Practice

  1. Add CI that runs the link checker on pushes and pull requests.
  2. Open a PR and confirm the check appears in its status.
  3. Cause a broken link in a local branch, observe the failed check, then fix it.
  4. Explain why a Pages deployment needs more permissions than a read-only check.
