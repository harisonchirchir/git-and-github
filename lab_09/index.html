Git Tags, Versioning, and GitHub Releases

Commits record development history; tags give important commits stable names, often for versions. GitHub Releases use tags to publish release notes and downloadable files.

Step 1: Understand tags

A lightweight tag is a name pointing to a commit. An annotated tag stores metadata such as tagger, date, and message; it is generally preferred for releases.

git tag
git tag -a v1.0.0 -m "Release 1.0.0"
git show v1.0.0
git tag -a v0.9.0 <commit> -m "Release 0.9.0"

Tags are not automatically included when pushing an individual branch. Push one tag or all local tags explicitly:

git push origin v1.0.0
git push origin --tags

Avoid moving or reusing published release tags. Teammates and automation may depend on each tag identifying the same commit.

Step 2: Apply semantic versioning

Semantic Versioning uses MAJOR.MINOR.PATCH:

  • MAJOR: incompatible public changes.
  • MINOR: backward-compatible functionality.
  • PATCH: backward-compatible fixes.

v2.4.1 is the first patch after 2.4.0. Pre-release identifiers such as v2.5.0-rc.1 indicate a release candidate. Document what counts as a breaking change for your project.

Step 3: Prepare and publish a release

  1. Ensure intended code is merged into the release branch and checks pass.
  2. Review changes since the prior release with git log --oneline v1.0.0..HEAD.
  3. Update version metadata and changelog if used; commit those updates.
  4. Create an annotated tag on the intended release commit and push it.
  5. Create a GitHub Release for that tag. Summarize user-facing changes, breaking changes, and migration steps; attach artifacts only when needed.
git log --oneline v1.0.0..HEAD
git tag -a v1.1.0 -m "Release 1.1.0"
git push origin v1.1.0

GitHub can generate release notes from merged PRs and related issues when repository settings and metadata support it. Review generated notes before publishing.

Step 4: Inspect and correct tags carefully

git tag --list "v1.*"
git show --no-patch v1.1.0
git ls-remote --tags origin

If a tag was created incorrectly and has not been shared, delete and recreate it locally:

git tag -d v1.1.0
git tag -a v1.1.0 <correct-commit> -m "Release 1.1.0"

If already pushed, coordinate with maintainers before changing it. Replacing a published release tag can make local references and artifacts disagree.

Practice

  1. Inspect history and identify a commit suitable for a practice release.
  2. Create an annotated pre-release tag and inspect it with git show.
  3. Push the tag to a test repository and create a GitHub Release with concise notes.
  4. Explain why a release tag should not be silently moved.
