Everyday Git: Inspecting Changes and Working with Remotes

Learn the everyday commands for inspecting your work, reading project history, and synchronizing local and remote branches safely.

Step 1: Understand the three local states

Git work happens across three local states: the working tree contains the files you edit, the staging area contains selected changes for the next commit, and the repository history contains recorded commits.

git status
git status --short

Use git status often. In short status, ?? means untracked, M means modified but unstaged, and M means staged. The first column describes the staging area; the second describes the working tree.

Step 2: Review changes before staging and committing

git diff                 # Unstaged changes
git diff --staged        # Staged changes
git diff -- README.md    # Changes in one file

Stage only the files or hunks that belong in your commit:

git add README.md
git add -p               # Interactively choose change hunks
git diff --staged
git commit -m "Document remote workflow"

git add . is convenient, but check status first so generated files, credentials, or unrelated edits do not enter the commit.

Step 3: Read and search project history

git log --oneline --graph --decorate --all
git show <commit>
git log --oneline -- README.md
git log -S"search text" --oneline

git log shows commits, git show displays a commit and its changes, and path-limited or -S searches help locate when a file or text changed. Use git diff <base>..<target> to compare commits or branches.

Step 4: Connect local and remote repositories

A remote is a named URL for another copy of the repository. origin is conventional, not a special Git keyword.

git remote -v
git remote add origin https://github.com/USERNAME/REPOSITORY.git
git remote show origin

git clone <url> creates a local copy and configures its remote. In a fork-based project, origin commonly points to your fork and upstream to the original repository:

git remote add upstream https://github.com/OWNER/REPOSITORY.git
git fetch upstream

Step 5: Fetch, pull, and push

git fetch downloads remote commits and updates references such as origin/main without changing your current branch or files. Review and integrate changes explicitly:

git fetch origin
git log --oneline HEAD..origin/main
git diff HEAD..origin/main
git merge origin/main

git pull fetches and integrates in one command. Its integration strategy may be merge or rebase depending on configuration; agree on a team policy. For an explicit rebase of your current private feature branch:

git pull --rebase origin main

Publish a branch with an upstream link for convenient future synchronization:

git push -u origin <branch-name>
git push

If a push is rejected because the remote has new commits, fetch and integrate them before retrying. Do not force-push shared history.

Step 6: Practice the daily loop

  1. Check status and the current branch, then fetch and review remote commits.
  2. Create or switch to a short-lived feature branch.
  3. Make a focused change; inspect with git diff.
  4. Stage intended files or hunks; review with git diff --staged.
  5. Commit clearly, push the branch, and open a pull request.
